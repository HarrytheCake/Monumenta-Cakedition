# CakeUI: agent reference

Client-only library mod (`cakeui`, package `io.github.harrythecake.cakeui`) for **Fabric and NeoForge on Minecraft 1.20.4, 1.21.1 and 26.1.2** (Cake multiloader layout, see `../tools/multiloader/README.md`; the Cakedition pack ships the Fabric 1.20.4 jar). Layout folders, written by pack developers with no Java, redraw the game window, launching screen, main menu, loading screens and HUD. Terms are in [`GLOSSARY.md`](GLOSSARY.md): layout, part, window, subwindow, element, port, declaration, game value, design pixel, skin, dev mode. The user-facing guide is [`README.md`](README.md); keep both files current.

The standalone repo is `HarrytheCake/CakeUI` (remote `cakeui`, a `git subtree` mirror pushed by `tools/push_all`; MIT; public since 2026-11-04). The source of truth is this folder in the Monumenta-Cakedition repo; never commit in the standalone repo. **Not in the pack yet:** the next pack release ships the newest CakeUI (0.2.0, no layout) together with CakeCosmetic (user, 2026-11-04). **Release v0.2.0** (multiloader, all six jars) was published from the mirror CI on 2026-11-05 at the user's request, ahead of CakeCosmetic.

## Decisions (grilled with the user 2026-10-30, Q1–Q35)

- **File-driven first** (ADR 0005, local): layouts in JSON5 plus a small expression language. The Java API (game values, element types, button actions) arrives in M5; a Java screen builder comes later.
- **Untouched unless mentioned** (ADR 0006, local): with no layout CakeUI does nothing and costs nothing. A port, button or HUD piece the layout doesn't name stays as vanilla and other mods draw it. Every hook checks this first.
- **Plugins may fill a port** (ADR 0008, local; 0.2.0, API version 2): `CakeUIApi.fillPort(port, owner, PortFiller)` for `main_menu/background` (panorama + overlay) and `loading_screen/background`. The filler draws when the active layout doesn't mention that port, also with no layout; a layout that mentions it wins; the filler returns false to leave vanilla. One filler per port (a second throws); a filler that throws is logged once and vanilla draws. First user: CakeCosmetic.
- **Plugins may add HUD pieces** (0.2.0, API version 2, for CakeMap; 2026-11-04): `CakeUIApi.addHudPiece(name, owner, HudPiece)`. `PluginHud.drawAll` runs at InGameHud.render TAIL before the late elements and the front layer (skipped with F1), each piece through `HudPart.piece`, so a layout that names it as a `hud` port can hide/move/scale/fade it and add elements; with no layout it is drawn as is. The Loader accepts added piece names as `hud` ports; the schema lists `minimap`. One mod per name, never a vanilla port's name; a piece that throws is logged once and switched off.
- **Parts:** window ⊃ game launching screen, main menu, loading screen, HUD ⊃ subwindows ⊃ elements. The pause menu and inventory will be built-in HUD subwindows (`hud/subwindow_pause`, `hud/subwindow_inventory`). Inventory slots never move. Chests and other screens come later.
- **Variables:** a folder sees its own and its parents' declarations, never a sibling's; a child's name shadows the parent's. **A folder writes only its own state variables** (a button's `set`/`toggle` must target the button's own folder).
- **Safety:** expressions have no loops and no file or network access. Button actions are client-side only: **never chat or commands**. Like every Cake mod, it downloads nothing at runtime.
- **Units:** `r` = design pixels (`design: [w, h]`, fit/fill/stretch), `px` = GUI pixels, `%` = parent. A plain number in a length is `r`; in `+`/`-` next to a length it is also `r`.
- **Dev mode** (`devMode` in config, off by default): a file watcher reloads, and the error overlay lists problems with file:line. **A reload with problems keeps the previous layout**; only the first load uses a layout with problems (broken elements skipped).
- **Performance:** zero work without a layout. Expressions are compiled once, and constants folded. Target under 0.5 ms/frame for a typical HUD on the low tier, to be checked with CakeBench in M4.
- **Pack:** stays out of the pack until a Cakedition layout exists (separate grilling). It will then ship on by default, with `layoutPath` set through yosbr.

- **HUD editor E1** (2026-11-07, ADR 0010, design in `docs/cakeui-design.md` "HUD editor"; local branch `hud-editor`): an in-game screen (`HudEditorScreen`; key `key.cakeui.editHud`, unbound; "Edit HUD…" on the settings screen, in a world only) where a player drags HUD pieces (vanilla's movable ports `HudDefaults.EDITABLE` + plugin pieces), scrolls to scale (0.05 steps, 0.25–4), right-clicks for hide/show, opacity (100/75/50/25), position mode (anchored / percent / fixed) and reset; snapping to screen edges/centre and other pieces (Alt = free), arrows nudge (Shift = 10), Ctrl+Z/Y, Done / Cancel / Reset all / Previews; Esc twice discards. **Personal edits** go to `config/cakeui/hud.json5` (`HudEdits`, core): one set per layout name, `vanilla` without a layout. **How they apply** (`HudPart.beginFrame`): the HUD part is active when the layout has a HUD, the active set has edits, or the editor is open; an edit's hide/opacity replace the layout's, and a move/scale is an **outer transform of the whole port** (vanilla piece + its elements; elements also take the edit's opacity) from `Placement.transform(edit, innerBox, w, h)`. The inner box is **measured**: `HudBounds` records every draw while a port's piece draws (1.20.4/1.21.1: `GuiGraphicsBoundsMixin` on `innerBlit`/`fill`/`drawString`/`renderItem` through the pose; 26.1.2: `GuiRenderStateBoundsMixin` on `GuiRenderState.add*`, using each state's `bounds()`), in coordinates without the editor's transform; unmeasured pieces use `HudDefaults.box` (also the previews). Anchored = nearest of 9 screen anchors + px offset; percent = fraction of the free space; fixed = top-left px. **26.1.2:** edited opacity has no effect on vanilla pieces (no shader colour there, as for layouts).
- **HUD editor E2** (2026-11-07): **layout edits**: in dev mode with a layout that has a `hud/` folder the editor starts on "Saving: layout" (toggle button above Done) and writes `hud/edits.json5` (`HudEdits.saveLayoutEdits`; deleted when empty; the Loader accepts the file in the hud part), loaded after the layout's files; the HUD uses `HudEdits.merge(layout edits, personal edits)` (a personal edit replaces each property it sets; the position as one). While saving into the layout, the player's own edits aren't shown. **The layout's own HUD elements** (top-level children of the hud part, key `@name`, in the files under "elements") can be moved/scaled/faded/hidden: with element edits (or the editor open) `HudPart.drawLayer` draws them one by one through `Renderer.drawPartKids` under the outer transform, measured like ports (`Paint.rect`/`texQuad` record too on 1.20.4/1.21.1; on 26.1.2 `rootCtx` starts `c.flat` from the GUI pose, since elements set the pose from it). **Other mods' pieces** (Q10): `HudExpect.expected(port)` (player state: survival, armor, air, riding …) and `HudBounds.hookedRecently` (every hook marks its port, hidden ones too): expected but not hooked = greyed, labelled "drawn by another mod", not draggable. "Show" writes `hide: false`, so it also undoes a layout's hide. Self-test: personal edits, then (dev-mode layout) layout edits incl. the first HUD element moved to the bottom-right, the file written and removed again.
- **HUD editor E3** (2026-11-07): **added elements** (key `+<type>-<4 hex>`, files: "added", each entry = position fields + `element`: an ordinary element definition, `AddedElements.defaults`): right-click empty space → Add text / box / bar / image (text and image open the panel at once); right-click one → Edit… / Delete. They're parsed with `Loader.element(layout, key, json5, file)` (the layout language's checks, cached by definition text) and drawn by `HudAdded` after the layout's front layer under the edit's transform, measured like the rest. A layout's own added elements (dev mode, `HudEditor.fromLayout`) use the layout's renderer (declarations, fonts, `assets/`); a player's use a small renderer without a layout whose `Layout.assets` is `config/cakeui/images` (`Layout.assets` is new; `Textures` takes the folder). **Properties panel** (`HudElementScreen`): text / size / colour / shadow; box: size, colour, outline; bar: value (0–1 expression), size, colour, background; image: file (PNG under the images folder, "Folder…" opens it), size; "Show only when" (stored as `visible: "= expr"`); a game-value picker (filter + 4 buttons; "All…" opens `HudValuesScreen`: every value with its live reading (`GameValues.preview`), filter, scroll, click to add it to the last field typed in; inserts `{name}` into a text, the bare name into an expression); problems from `HudAdded.check` (a probe `Layout` sharing the real scope) under the title; Done keeps, Cancel restores the definition; each edit session is one undo step. The editor stays open under the panel (`childOpen`).
- **HUD editor E4** (2026-11-07): **style presets** (`StylePresets`, core): right-click health / hunger / armor / air / mount health → Style: bar, number, bar + number; XP: slim bar, level only. A preset sets the port's `style` and `hide`, and adds one group element `+style-<port>` (bars + language-free numbers, shown only when vanilla would show the piece) where the piece was; a styled port draws neither its vanilla piece nor the layout's elements for it (`Port.styled`), and the editor shows only the preset element (Delete = back to vanilla). New game values `player.exhaustion` (the client's estimate; servers don't send it; 26.1.2 reads it through `FoodDataAccessor`), `player.survival`, `mount.health`, `mount.maxHealth`. **item** elements take the player's slots (`item: "slot:mainhand|offhand|head|chest|legs|feet|<0-40>"`, `InventorySlots`), **inventory** is a new element type (`slots`: hotbar, main, armor, offhand, all, "9-17", "0,40"; `columns`, `gap`, `slotBackground` vanilla/rect/none, `slotColor`); in the panel, item = "Shows" (held item, offhand, head, chest, legs, feet, slot number…, item id…) and inventory = "Slots" (hotbar, main, all, armor, offhand, custom…) choices with a hint line of slot numbers; every added element has a Scale field (`edit.scale`, same as scrolling). Both have `counts`, `durability`, `cooldown` (each on/off; `render/ItemDraw` per version; on 26.1.2 all three on = vanilla's `itemDecorations`). **Crosshair styles** (`CrosshairStyles`; stored as the crosshair port's `element` with `type: "crosshair"`): dot, cross, circle, image; size, gap, thickness, colour, invert. `GuiCrosshairMixin` wraps only vanilla's crosshair sprite blit (ordinal 0) in `renderCrosshair` / 26.1 `extractCrosshair`, so the attack indicator stays; `Renderer.drawCrosshair` draws through `Paint` with `Paint.invert` (1.20.4/1.21.1: vanilla's inverting blend func; 26.1.2: `GUI_INVERT` / `CROSSHAIR` pipelines). **Animated images**: `.gif` and `.webp` for every image (and crosshair image): `render/AnimatedImages` (core, tested) decodes GIF with Java's reader and WebP by cutting each ANMF frame into a WebP of its own for TwelveMonkeys' reader, composites them (offsets, blending, disposal) and **fits** big files instead of refusing them: frames scaled down (alpha-weighted area average) to at most 512 px a side and 8 M pixels for all frames together, beyond 256 frames every n-th kept (times merged); only sources over 8192 px are refused. Decoding runs on a daemon background thread (`Textures.DECODER`; the image shows once ready; the user's 384 x 384 x 208-frame WebP takes about 6 s and comes out 200 x 200). `Textures` packs the frames in a near-square **grid** (keeps the texture under GPU limits) with the frame times (`Tex.frames`, `delays`, `cols`, `frameAt`, `uv`, `frameW/H`); an image without its own "frames" plays the file's times. Problems name the folder looked in (`assets/` or `images/`). **Bundled libraries** (`gradle/cakeui-libs.gradle`, `twelvemonkeys_version` in gradle.properties): TwelveMonkeys imageio-webp, imageio-core, imageio-metadata, common-image, common-io, common-lang 3.12.0 (BSD-3, licence in `META-INF/licenses/`), `include` on Fabric, `jarJar` on NeoForge; jars are about 1 MB now.
- **HUD editor E5** (2026-11-07, **API version 3**): `CakeUIApi.addMovables(owner, MovableSource)` (a mod's `Movable`s: `id`, `label`, `box`, `place`, `resizable`, `save`, `cancel`; `HudMovables`, editor keys `~owner:id`): things a mod places itself (CakeChat's chat windows, CakeMap's minimap). The editor lists them, drags them (`place` live), resizes resizable ones (bottom-right handle, or scrolling ×1.05), records their boxes in each undo step, on Done calls `save` for those that changed, on Cancel (and when the editor is closed another way) puts every box back and calls `cancel`; it never stores them in hud.json5. `CakeUIApi.openHudEditor(parent)` opens the editor (false outside a world). `HudPiece.editable()` (default true): false = left out of the editor (full-screen pieces, or ones the mod places as a movable); `HudEditor.migrate` moves an old personal edit on such a piece once to the mod's movable of the same id (or drops it) and saves hud.json5. Self-test: a stand-in movable registered with `-Dcakeui.selftest` is moved and must be saved on Done. CakeChat reaches this API by reflection (no dependency); CakeMap compiles against it (so it needs CakeUI 3 to build).
- **UI editor E6** (2026-11-07, user's request: "this way of editing on any UI we support"): `HudEditorScreen.openFor(screen)` edits a screen CakeUI redraws, drawn live under the editor (`target.init` / `target.render` with the mouse far away; the editor takes all input): the main menu, the pause menu, the inventory and loading screens (a "saving" message screen as the preview, `ScreenEditTargets`). Pieces: every button (`<part>/button:<id>`, `#<index>` for a repeated id; moved/scaled by `ScreenPorts.applyEdit` on top of the layout's or vanilla's box (`LAYOUT_BOX`/`ORIGINAL`), hidden with `visible`) and the vanilla pieces drawn through `ScreenPorts.vanillaPiece` (main menu logo, splash, version; inventory title; loading text and map), which take the edit as an outer transform and are measured (`HudBounds`, keys `<part>/<piece>`; `afterScreenRender` ends the measuring frame). Same files and save targets as the HUD (`ScreenPorts.part()` = "main_menu", "pause", "inventory", "loading_screen"); HUD code skips keys with "/". Opened with the Edit HUD key on such a screen (`screenKeyPressed`) or from the settings screen (Main menu… / Pause menu… / Inventory… (in a world) / Loading…). Not on screens: opacity, styles, adding elements, the layout's own elements of those parts; the game-launching overlay (no screen, no cursor) stays layout-only. Self-test: main menu (Singleplayer moved, logo hidden) and pause menu (Back to Game moved) edited, Done, checked on the real screens; also one button on each dragged through the editor's own mouse handlers (`mouseDragStart`/`mouseDragCheck`, as a player opens it: dev mode saving into the layout).
- **Editor toolbar placement** (2026-11-08, user's report: "can't interact" with the pause menu of the test layout `window_cake`): the toolbar (Done/Cancel/Reset all/Previews, the save-target button above, the help below) took the clicks for any piece under it, and a layout's pause menu puts tiles where it was (left, half-way down). `placeBar()` (in `init`) now takes the first place that covers no visible piece: left-middle, right-middle, top-left, top-right, bottom-left, bottom-right; else the one covering the least. **H** hides the toolbar and help (a hint at the top says H shows them again). Self-test with a copy of `window_cake`: the pause drag passes (it failed before). H itself is not self-tested.
- **Test status (user's rule 2026-11-07: game runs only on Fabric 1.20.4):** E5's and E6's self-tests ran on Fabric 1.20.4 only; NeoForge 1.20.4, Fabric/NeoForge 1.21.1 and 26.1.2 were built and unit-tested, not run.

## Plugins (API, for CakeMap, CakeCosmetic and other mods)

API version 3 (HUD editor, 2026-11-07) adds `addMovables` / `Movable` / `MovableSource`, `openHudEditor(parent)` and `HudPiece.editable()`; see "HUD editor E5" above. Raise `mod_version` to 0.3.0 when releasing it (CakeMap needs it; CakeChat checks `VERSION >= 3` by reflection).

A plugin is a class implementing `io.github.harrythecake.cakeui.api.CakeUIPlugin` with a public no-argument constructor. CakeUI runs every plugin once, before the first layout loads.

- **Fabric:** `"entrypoints": { "cakeui": ["com.example.MyCakeUIPlugin"] }` in `fabric.mod.json` (unchanged since 0.1.0). Run in CakeUI's client initializer.
- **NeoForge:** a service file in the plugin's jar, `META-INF/services/io.github.harrythecake.cakeui.api.CakeUIPlugin`, containing the class name (one line). CakeUI reads it with `ServiceLoader.load(CakeUIPlugin.class, CakeUIPlugin.class.getClassLoader())` in `FMLClientSetupEvent.enqueueWork` (NeoForgePlugins); a broken entry is logged and skipped. A plugin mod that only *optionally* uses CakeUI can ship the file anyway: without CakeUI nobody reads it. Mark CakeUI `type = "optional"`, `ordering = "NONE"` in its `neoforge.mods.toml` / `mods.toml` if it wants it listed.
- The API's package and class names (`CakeUIApi`, `CakeUIPlugin`, `ElementType`, `ElementContext`, `ButtonAction`, `PortFiller`, `HudPiece`, `PropKind`) are the same everywhere; Minecraft's types in their signatures follow the version: `GuiGraphics` (1.20.4, 1.21.1) or `GuiGraphicsExtractor` (26.1.2), `Screen`. So a plugin compiles per version against `build/libs/cakeui-<loader>-<mc>-0.2.0.jar` (compileOnly; the API classes are in the common part, identical on both loaders of one version). `CakeUIApi.VERSION` stays 2. The JSON5 reader (`io.github.harrythecake.cakeui.json`) is in every jar too.
- On 26.1.2 a plugin draws into the frame's render state like vanilla (`GuiGraphicsExtractor.pose()` is a 3x2 matrix; no shader colour: apply `ElementContext.opacity()` to your colours).

## How drawing works

This describes 1.20.4 (the shipped target); 1.21.1 works the same way, 26.1.2 differs where the "Multiloader status" section says. Fabric API events are the loader events of CakeUIClient's hooks (NeoForge: ScreenEvent.*, RenderGuiEvent, ClientTickEvent).

- **One renderer per loaded layout** (`Renderer`). `beginFrame` sets the frame number, design scale (`rx`, `ry`), mouse and time. `drawPart`, `drawElements`, `drawSingle` and `drawSkin` walk nodes.
- **Per node:** visible → size (defaults: text = measured, image = texture size in r, background = parent's full size, item 16r, button 200×40r, bar 100×8r, containers = parent) → place (anchor/origin, or the row/column cursor) → transform (+ parallax) → hover by inverting the transform (2D) or by `Geometry.unproject` (3D) → content → children.
- **3D** (rotateX/rotateY/z ≠ 0): the content is drawn flat into a window-sized offscreen buffer (`Layers.push`, box at a margin of 10% of the screen), then the whole buffer is drawn as one quad through `Geometry.projection` (a real perspective matrix, so text, items and nested 3D tilt correctly). Buffer colours are premultiplied, so composite uses ONE, ONE_MINUS_SRC_ALPHA. Vanilla's `Framebuffer.clear()` unbinds, which is why `push` clears first and then binds. Nested 3D works with one buffer per depth.
- **Why buffers:** vanilla's `VertexConsumer.vertex(Matrix4f, …)` drops `w`, so a perspective matrix on the MatrixStack can't work.
- **States:** `Prop.pick(hovered, pressed, disabled)`. Number, length and colour props with states ease through `NodeState.Anim` when `transition.duration > 0`.
- **Clicks:** the topmost hovered enabled `button` of the frame takes the click (`ScreenMouseEvents.allowMouseClick` returns false). The action runs on press.
- **Loading screens:** six vanilla screens (`LoadingPart.kind`). Their background is one hook on `Screen.render`'s `renderBackground` call; per-frame start and the front layer use Fabric's `ScreenEvents.before/afterRender` (ReconfiguringScreen has no render method to mix into).
- **Launch overlay:** `SplashOverlay` draws no screen of its own: no clicks, no cursor. First start: vanilla clears the window (a hidden background clears to black); reloads: a fading fill, whose alpha the background elements use. Minecraft's font only exists after the first load: layout fonts work, vanilla-font text doesn't.
- **Window:** applied on the first client tick (the window exists) and after every reload; game values in title/border are re-read twice a second (`env.frame` is bumped, since nothing is drawn there).
- **HUD:** `HudPart.beginFrame` (InGameHud.render HEAD) reads each mentioned port once into a `Port`; hooks only read it. Back layer at render's first `getCurrentGameMode()` (after the full-screen overlays), front + action bar/title port elements at TAIL; status-bar port elements at renderStatusBars TAIL. Nothing with F1. `Renderer.beginFrame` keeps the time step when the HUD and a screen both start the same frame (< 2 ms apart).
- **Built-in subwindows** (`Loader.BUILTIN_SUBWINDOWS`: `hud/subwindow_pause`, `hud/subwindow_inventory`): loaded as type `part` into `part.builtins`, never `children`, so the HUD won't draw them. Ports per screen in `Loader.PORTS` (`hud/pause`, `hud/inventory`). Drawn like a part (`drawPart`, back/front) while their screen is open. Pause: only `showMenu` (F3+Esc stays vanilla). Inventory: back layer after the dim, panel port elements right after the panel texture via `drawElementsIn` (panel box, follows the recipe book), title port elements + front layer just before the item tooltip.
- **Skins:** `ScreenPorts.applyButtons` (every frame) moves, resizes, hides and relabels buttons and registers skins. `ClickableWidgetMixin` draws the skin instead of `renderWidget`, so the vanilla button still handles input. Inside a skin, every element's hover = the button's hover.
- **Small CJK text** (`readable`, default true): in Minecraft's bitmap font, text containing CJK (`Renderer.hasCjk`) is enlarged to at least 2 screen px per font unit (vanilla's GUI scale 2): its 16×16 glyphs sit in 8 units, so below that nearest sampling drops whole rows ("squeezed" Chinese, reported by the user 2026-11-04 at 852×475). Linear filtering was tried and rejected: soft but still unreadable at ~11 px. Latin text and layout TTFs keep the design size. `-Dcakeui.size=852x475` runs the dev client at that size.
- **Fonts:** a layout TTF is built per sharpness step (oversample 1/2/4/8/16 by on-screen scale). Minecraft's fonts are borrowed as fallbacks (wrapped so closing ours never closes theirs), and everything is rebuilt when Minecraft reloads its fonts. Tested in game with Bahnschrift + Chinese fallback (dev run, 2026-10-30).

## Invariants

- No layout = no work: every mixin returns to vanilla when `TitleMenu.port(…)`/`part()` is null.
- Problems never crash the game: load problems skip the broken element; runtime expression errors give the default and are listed once.
- Never send chat or commands; never download anything.
- Test data uses made-up names; no real player names anywhere.
